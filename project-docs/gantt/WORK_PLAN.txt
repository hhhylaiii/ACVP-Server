================================================================================
CAVP 產學合作計劃（FIPS 203/204）— 開發工作說明
================================================================================

專案目標：為合作公司建立自裝式網頁工具，讓非密碼專業人員不需 CLI 指令，
        即可驗證其密碼模組（IUT）的 FIPS 203（ML-KEM）/ FIPS 204（ML-DSA）
        實作是否正確。底層複用 NIST ACVP-Server 的 Gen/Val 引擎。

期程：10 週，2026-06-22（W1 週一）~ 2026-08-28（W10 週五），一週一個 Sprint。
週次對照：
  W1  06/22–06/26      W6   07/27–07/31
  W2  06/29–07/03      W7   08/03–08/07
  W3  07/06–07/10      W8   08/10–08/14
  W4  07/13–07/17      W9   08/17–08/21
  W5  07/20–07/24      W10  08/24–08/28

工作分為三塊平行軌：
  [A] 後端（Backend, Dev A）
  [B] 前端 / UX（Frontend / UX, Dev B）— 設計需求高
  [C] 整合包 / 封裝（Integration / Packaging, Dev C）

里程碑：
  M1（W1 末 06/26）程式化呼叫打通
  M2（W4 末 07/17）後端全模式 + 整合包定版
  M3（W5 末 07/24）端到端整合驗證通過
  M4（W7 末 08/07）瀏覽器端到端跑通
  M5（W8 末 08/14）非專家可獨立操作
  M6（W10 末 08/28）自裝包交付 + 簽核


================================================================================
[A] 後端（Backend, Dev A）
================================================================================
主責：Web API、IGenValInvoker 整合、Orleans client 接線、非同步工作。
重點期：W1–W4 為主要開發；W5 起轉為支援前端整合與後續封裝。

W1（S0）地基與程式化 spike — 全案最關鍵的去風險
  - 確認 repo 可建置、Orleans Silo 可正常啟動。
  - 核心 spike：寫一個最小 .NET host，程式化呼叫 IGenValInvoker，
    完成 ML-KEM keyGen 的 Generate + Validate，全程不經 CLI。
  - 移植 AutofacConfig 與 Orleans client 接線到獨立 host。
  - 建立後端 repo 骨架與 CI。
  - 產出：證明「程式化出題 + 批改」可行的測試程式。→ 里程碑 M1

W2（S1）後端 API 核心
  - 建立 ASP.NET Core 8 Web API。
  - 三個端點（小資料同步版）：
      POST /check     檢查 registration 參數是否合法
      POST /generate  產生 prompt.json（題目）
      POST /validate  收 responses.json，回 validation.json（批改結果）
  - 產出：以 curl / Postman 對 ML-KEM keyGen 完成出題 + 批改。

W3（S2）後端全模式覆蓋
  - 覆蓋全部 5 種演算法 × 模式：
      ML-KEM：keyGen、encapDecap
      ML-DSA：keyGen、sigGen、sigVer
  - 確認各參數集（ML-KEM-512/768/1024；ML-DSA-44/65/87）皆可出題 + 批改。

W4（S3）非同步背景工作 + 輸入驗證
  - 長時間 generate / validate 改為「背景工作 + 輪詢狀態端點」，避免 HTTP 逾時。
  - 提供 registration 預設集（讓前端帶安全預設值）。
  - 伺服器端輸入驗證（不信任前端送來的參數）。
  - 產出：後端 5 模式皆可經 API 出題 + 批改。→ 里程碑 M2（與 C 軌整合包定版同步）

W5（S4）支援端到端整合測試
  - 配合 C 軌做內部端到端測試（範例向量），修正後端發現的問題。
  - 凍結並文件化 API 介面（給前端對接用）。

W6（S5）支援前端串接
  - 協助前端接 /generate、/validate 與非同步輪詢端點。
  - 修整合過程暴露的後端 bug。

W7（S6）配合瀏覽器端到端
  - 配合前端把全部 5 模式在瀏覽器端跑通所需的後端調整。→ 里程碑 M4

W8（S7）配合報告與錯誤訊息
  - 提供報告畫面所需的後端資料（逐題 pass/fail、摘要欄位）。
  - 後端層級的輸入錯誤回報，配合前端做欄位級錯誤訊息。

W9（S8）配合封裝
  - 後端容器化（Dockerfile），與 Orleans Silo 容器以 docker-compose 串接。
  - 提供可調參數（例如 MaxConcurrentWork）。

W10（S9）UAT 修正
  - UAT 期間後端 bug 修正、黃金測試（與 CLI 結果比對）後端側確認。→ 里程碑 M6


================================================================================
[B] 前端 / UX（Frontend / UX, Dev B）— 工作量最重的一軌
================================================================================
主責：UI/UX 設計、操作流程、成績報告畫面、英文使用文件。
因對方為非技術人員，設計品質要求高，故此軌自 W3 提前並行起步、吃到 W8，約 6 週。

W1–W2（前置，與後端 spike 並行）
  - UX 研究：理解非專家操作情境，列出術語小辭典需求。
  - 決定前端框架（React + Vite 或 Blazor，取團隊最熟者）。
  - 競品 / 既有 ACVP 工具參考，畫初步線框草稿。

W3–W4（S2–S3）設計系統 + 線框 + SPA 骨架
  - 建立設計系統（色彩、字體、元件樣式、卡片式版面）。
  - 完整線框稿：演算法選擇 → 參數 → 產生 → 下載 → 上傳 → 報告。
  - 搭建 SPA 專案骨架、路由、API 串接層（與後端並行，不等後端全好）。

W5–W6（S4–S5）核心操作流程 UI
  - W5：選演算法 / 模式（卡片式）→ 勾參數集 → 進階選項給安全預設 →
        按「產生測試向量」→ 下載 prompt.json + 操作說明。
  - W6：上傳 responses.json → 觸發批改 → 串接後端非同步輪詢 → 結果頁雛形。

W7（S6）端到端整合
  - 前端接後端全部 5 模式，先讓單一演算法在瀏覽器端到端跑通，再擴及全部。
  - 產出：瀏覽器端到端可出題 + 批改。→ 里程碑 M4

W8（S7）UX 打磨 + 成績報告
  - 友善預設值、提示文字、術語小辭典、隱藏進階選項。
  - 強健錯誤訊息：上傳格式錯誤精確定位到 tcId / 欄位級別，並附修正提示。
  - 可讀成績報告：摘要 + 逐題 pass/fail、醒目標示失敗項、可下載 validation.json。
  - （選用）歷史清單（搭配 SQLite）。
  - 產出：非技術人員無需 CLI 即可獨立操作。→ 里程碑 M5

W9（S8）配合封裝與文件
  - 前端 build 產物打包進 Docker。
  - 製作英文使用手冊（含操作截圖）。

W10（S9）UAT 修正
  - UAT 期間前端 / UX bug 修正與細節調整。→ 里程碑 M6


================================================================================
[C] 整合包 / 封裝（Integration / Packaging, Dev C）
================================================================================
主責：公司端整合支援物（範例 harness、欄位文件、範例檔）、Docker 封裝、
      黃金測試、UAT 驗收。此軌處理「最關鍵的去風險」：公司如何產生 responses.json。

W1–W3（前置與準備）
  - 研讀 ACVP 規格（~/Project/ACVP）中 ML-KEM / ML-DSA 的 JSON 欄位定義、
    測試型態（KAT / MCT / MMT）。
  - 撰寫範例 harness 草稿（ML-KEM / ML-DSA 各一份 Python 範本），
    把「讀題 → 呼叫模組 → 寫答」骨架先搭好。
  - 規劃黃金測試（與 GenValAppRunner CLI 比對的自動化測試）。

W4（S3）整合包定版
  - 定版公司端整合支援物（搭配後端全模式產出）：
      1. 範例 harness：ML-KEM / ML-DSA 各一份，只留「呼叫自家模組」那一行讓公司填。
      2. 欄位對照文件：逐演算法列出 prompt 輸入欄位、responses 應填輸出欄位，
         標明編碼（hex / base64）與位元組長度。
      3. 範例檔：每個 prompt.json 附「對應的範例 responses.json」與操作說明。
  - 產出：整合包初版。→ 里程碑 M2（與 A 軌後端全模式同步）

W5（S4）內部端到端整合測試（不需公司中途配合）
  - 用 NIST 範例向量做完整端到端測試：出題 → 範例 harness 當假 IUT → 批改。
  - 驗證整條工具鏈正確、及早抓 JSON 格式問題。
  - 產出：端到端整合驗證通過。→ 里程碑 M3

W6–W7（黃金測試與整合協助）
  - 執行黃金測試：網頁驗證結果須與 CLI 結果一致。
  - 協助 A / B 軌整合，記錄並回報問題。

W8（文件整備）
  - 整理英文交接文件、整合包說明，準備封裝所需內容。

W9（S8）Docker 封裝 + 英文使用手冊
  - 撰寫 Dockerfile + docker-compose（Web 容器 + Orleans Silo 容器），一鍵啟動。
  - 可調 MaxConcurrentWork 等參數，於 Linux + Windows 各測一次。
  - 完成英文使用手冊（給公司操作者與工程師各一份視角）。

W10（S9）UAT + 驗收
  - 與公司做 UAT（先 sample 向量、再真實向量），收集問題並協調修正。
  - 最終黃金測試比對、交付自裝包 + 全部文件、取得驗收簽核。→ 里程碑 M6


================================================================================
驗收標準（交付前確認）
================================================================================
  - 非專家僅透過瀏覽器即可對全部 FIPS 203/204 模式出題並驗證回應。
  - 公司端以單一 docker compose up 完成自裝。
  - 網頁驗證結果與 CLI 結果一致（黃金測試比對通過）。
  - 文件足以讓公司獨立操作（含 prompt / responses 格式說明與範例 harness）。

備註：與公司的接觸集中在最後 W10 的 UAT / 驗收；前 9 週可獨立完成整個產品，
      中途不依賴公司配合（格式風險由範例 harness、欄位文件與 W5 內部端到端測試把關）。
